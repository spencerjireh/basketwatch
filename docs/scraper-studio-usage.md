# How Basketwatch uses Bright Data Scraper Studio

Bright Data Scraper Studio is the collection engine and the self-healing
mechanism. It is not an add-on to the project; it is the single production
path for getting prices out of store websites and into the database.

## Two roles, one service

Scraper Studio fills two roles in the system, and both run through the same
Bright Data API:

1. **Collection.** Every pull of a store's prices goes through a Scraper
   Scraper Studio collector -- a scraper whose extraction logic was generated by
   Scraper Studio's AI from a seed URL and a plain-language description of
   what to extract. Twelve of the sixteen stores in the fleet run this way.
   The four exceptions expose a structured `/products.json` endpoint that
   returns the full catalogue without browser rendering. Those four still
   feed the same database tables and the same validator.

2. **Self-healing.** When a store changes its layout and the collector
   breaks, the system sends the broken output to Scraper Studio's
   `refactor_template` API with a prompt describing what went wrong.
   Scraper Studio rewrites the collector's extraction logic in place. The
   fix is verified against a canary pull before it is saved to production.
   Scraper Studio is not just how we get data; it is how we repair the
   thing that gets data.

## The collection pipeline

A scheduled pull (twice daily, or triggered manually) follows this path:

1. **URL selection.** The puller builds a bounded list of product URLs for
   the store. For product-page collectors, this comes from the store's
   sitemap filtered to staple categories. For listing-page collectors, it
   is a single seed URL with pagination. The list is capped at a
   configurable page ceiling per store to prevent unbounded crawls.

2. **Scraper Studio execution.** The URL list is passed to
   `brightdata scraper run` via the CLI. Scraper Studio renders each page
   in a cloud browser, runs the collector's extraction logic, and returns
   structured JSON rows. Each row contains the product name, price,
   currency, stock status, URL, and size where available.

3. **Validation.** The returned rows are checked against a stored baseline
   for the store. Four checks run: schema conformance, null-rate spikes,
   row-count anomalies, and price-drift detection. A run that passes
   updates the baseline; a run that fails opens an incident with the
   specific check results as evidence.

4. **Persistence.** Clean rows are diffed against the previous pull. Only
   price changes are written (change-only history), so the database
   captures when prices move without storing redundant snapshots. Every run
   records its row count, page count, and transport source, which is what
   lets the validator tell a truncated pull from a genuine price crash.

## The self-healing loop

When a pull fails validation, the system opens an incident and -- if
auto-heal is enabled -- begins repairing the collector autonomously:

1. **Diagnosis.** The failed output is compared field by field against the
   last healthy baseline. The system identifies which fields are missing,
   which have unexpected types, and whether the failure is a null-rate
   spike (key fields returning null where they previously had values) or a
   row-count collapse (the collector returned a fraction of the expected
   rows).

2. **Prompt composition.** A targeted heal prompt is composed from the
   diagnosis. The prompt names the specific broken fields and what they
   should contain, following guidelines derived from structured
   experiments: small and specific beats broad, naming the page element
   beats describing the data, and including a sample of the broken output
   helps Scraper Studio understand the failure.

3. **Proposal.** The prompt is sent to Scraper Studio's `refactor_template`
   endpoint, which rewrites the collector's extraction code. Scraper
   Scraper Studio returns a diff showing what changed and a preview of the new
   output.

4. **Judgement.** The preview output is validated against the project's
   baseline checks (a relaxed variant that accounts for the small sample
   size of a preview). If the preview passes, the fix is approved; if it
   fails, the fix is rejected with feedback and a new attempt begins. Each
   store is capped at a configurable number of attempts per incident and
   per day.

5. **Verification.** An approved fix triggers a canary pull -- a real
   execution of the updated collector against the store's live pages. The
   canary output goes through the full validation pipeline. If it passes,
   the incident is resolved. If it fails, the system either re-proposes
   with the canary's failure details or escalates to manual attention.

Every step of this loop is persisted: the evidence bundle, the prompt sent
to Scraper Studio, the diff Scraper Studio proposed, the preview output,
the canary result, and the final verdict. The dashboard's
[Self-healing](https://basketwatch.spencerjireh.com/healing) page renders
the full audit trail for every attempt.

## Budget controls

Scraper Studio calls cost credits, and the project has a finite budget. Three
controls prevent runaway spend:

- **Per-incident cap** (`HEAL_MAX_ATTEMPTS_PER_INCIDENT`): limits how many
  times the loop retries a single broken store before escalating.
- **Per-scraper daily cap** (`HEAL_MAX_PER_SCRAPER_PER_DAY`): prevents a
  store that keeps breaking from consuming the day's budget.
- **Bounded crawl scope**: every collector's creation description includes
  an explicit scope clause ("this product page only; do not follow links")
  to prevent the kind of unbounded crawl that once cost $26 in a single
  session during development.

## The collector manifest

[`collector-manifest.json`](collector-manifest.json) is the fleet registry.
It records every store's seed URL, the plain-language description used to
create its Scraper Studio collector, the structural findings from probing
the site (what markup it uses, whether it renders client-side, what price
format it publishes), and the resulting collector ID. The manifest is read
at runtime by the API's provisioning service, which can recreate any
collector on any Bright Data account from the definitions stored there.

## Parker's Pantry: the controlled demo target

[Parker's Pantry](https://pantry.spencerjireh.com) is a fictional grocery
store we host ourselves, with a US storefront and a Philippine twin. It
exists so the self-healing loop has a target we are allowed to break on
purpose. A layout switch flips the storefront between two markup structures;
the next scheduled pull sees the break, the loop fires, and Scraper Studio
repairs the collector -- all without human intervention.

The store is fully disclosed: its prices are generated (a deterministic
daily walk from fixed base prices), both storefronts are labeled as test
data, and they never contribute to the country price index.

## What this proves

The combination of Scraper Studio as collector and Scraper Studio as healer
means the system has a single mechanism for both getting data and repairing
its own data pipeline. A store layout change is not a support ticket; it is
an event the system detects from output anomalies, diagnoses from
field-level evidence, and resolves by asking Scraper Studio to rewrite the
extraction logic --
verified by a real re-scrape before the fix goes live.
